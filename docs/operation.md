# 運用の決まり（地図を回し続けるために）

地図は、書き方がそろい、古いものを片付け続けて初めて正しく働く。片付けは、実装担当者が毎日の見直しで行う。ここでは、誰が・いつ・何をするかを決める。
書き方そのものは `CLAUDE.md`、地図の見方は `README.md` にある。

## 1. 役割

| | 人 | Claude |
| --- | --- | --- |
| 決める | マージする・Issue を閉じる・カタログに機能を足すか・決まりを変えるか・使わない機能を外すか | 決めない（案を出す）。ただし自分の書き方の足りないものは、見直しで自分で直す |
| 作業 | 頼む・見直しの案から選ぶ | 地図を読んでから作業する・書き方を守る・PR を出す・決まったことを実行する（閉じる文面、カタログの PR） |
| 確かめる | 地図と守り具合を見る | マージのあと、本番に出たか（デプロイ）を確かめる |

## 2. 毎回の作業（Claude）

1. **前**：コネクタで `map` → `feature` → `issue` を読む。どの機能・どの Issue の作業かを決める（決められなければ聞く）
2. **中**：`CLAUDE.md` の書き方で Issue と PR を書く
3. **出す前の自己チェック**：コネクタの `check` に下書き（kind・title・body・files）を渡し、✗ を直してから出す
4. **PR**：説明の最後に申告の3つの見出し
5. **出したあとの自己チェック**：`check` に PR か Issue の番号を渡す。✗ があれば題・説明を直す
5a. **マージの前**：PR の CI のチェック「test」（型・単体テスト・画面のテスト）が success かを確かめる。失敗・まだのときはマージしない（人の OK があっても、先に知らせる）
6. **マージのあと**：本番に出たかを確かめる（GitHub の main のチェック「Workers Builds」が success か）。失敗していたら、すぐ人に知らせる。確かめずに次へ進まない
7. **画面を変えたとき**は、デプロイに加えて、変えた画面を開いてエラーが出ないかを見る。本番の画面を開けないときは、手元で同じ画面を開いて確かめ、人に本番で開いてもらうよう頼む（#38 でクラスターが壊れたまま出た反省）

## 2a. ほかの AI がこのコネクタで作業するとき

CLAUDE.md を読まない AI（別の会話の Claude、ほかの会社の AI など）でも、同じ決まりで作業できるようにする。
- 最初に `rules` を読む：書き方の決まり（9つ）と、そのリポジトリで使える機能名の一覧が返る
- 出す前と出したあとに `check` で自己チェックする（上の 3・5）。返るのは ✓／✗ と直し方だけで、判断はしない
- チェックの中身：PR は「題の頭が機能名」「変えたファイルが一覧の機能に当たる」「題の機能とファイルの機能が合う」「関係する Issue を書いている（閉じた Issue を Closes していない）」「申告の3つの見出し」。Issue は「題の頭が機能名」「本文の『機能：』が一覧の名前」「『閉じる条件：』がある」と、同じ機能の開いた Issue があれば知らせる（やり残しなら、そちらに足す）
- 人は、毎日の見直しの守り具合で、どの AI の作業でも同じ物差しで見られる

## 3. 毎日の見直し（実装担当者が行う）

- **誰が**：その日に作業する実装担当者（Claude でも、ほかの AI でも）。定期の自動作業にはしない
- **いつ**：その日の最初の作業の前。地図（`map`）の先頭に「毎日の見直し：今日はまだ」と出たら、`review` を読む（読むと見直した時刻が残り、「今日は済み」になる）
- **中身**：前回の見直しからの新しいものだけを、3つに分けて出す
  1. **自分で直すもの**：書き方の足りないもの。自分の PR・Issue なら、題・説明をその場で直す（決まりから導けることなので、人に聞かずに直してよい）。ほかの人のものは 2 に回す
  2. **人に決めてもらうもの**：どの機能にも当たらない作業（カタログに足すか）・申告の「足りなかった決まり」（**決まりに足すか、一回限りか**。よく出るものは足す案に）・新しく出てきた話題（タグ。**機能に上げる／別名にまとめる／話題のまま**）
  3. **人の判断を待っているもの**：古くなっている候補の Issue・直近7日マージなしなのに開いた Issue がある機能・画面のないデータ。前からのものなので、**数が増えたときだけ**人に伝える
- **人への伝え方**：その日の最初の返事の頭に短く。1 は直したことを1行で、2 は案を添えて、3 は増えたときだけ。何も無ければ「見直し：変わりなし」と1行
- **決まったら**：実装担当者が実行する（Issue を閉じる文面・カタログや決まりの PR）。人の OK なしに閉じたり消したりしない

## 4. カタログ（機能の一覧）の直し方

- 新しい機能は、作った PR の中で `src/catalogs.ts` に足す
- 名前を変えるときは、前の名前を `aliases` に残す（過去の PR・Issue の題を拾い続けるため）
- 機能を消す・まとめる前に、人に聞く
- `check` は、いま本番にあるカタログで判定する（PR の中のカタログで自分を合格にしないため）。そのため、カタログを直す PR では「ファイルが機能に当たらない」「題の機能とファイルの機能がずれる」の ✗ が出ることがある。その ✗ がカタログの直しのせいだけなら、PR の「決まりになく、自分で判断した所」に理由を書けばよい（マージのあとに `check`（番号）で ✓ になるのを確かめる）
- 見た目・文書・テストのように、ほかの作業にもついてくるものは `fallback`（ほかに当たらないときだけ数える）

## 4a. タグ（複数の入り口）

- 本文に「タグ：コールドムーン、絵本」を1行（PR・Issue どちらでも。3つまで。@ や # は付けなくてよい）
- 機能の名前・別名と同じタグは、その機能にも入る（1つの作業を、複数の機能から見つけられる）
- それ以外は「話題」。カタログを増やさずに束ねる軽い入り口で、地図のクラスターとコネクタの `feature` から入れる
- **作品ごとなど、機能の中の話題**はカタログの `topics` に置く（例：満月の物語の中の「コールドムーン」「ビーバームーン」）。タグか、題に作品名があればその話題に入る。別名（`aliases`、題の頭の照合用）とは分けて持つので、作品のタグが機能名に吸い込まれない
- 散らからないように：新しい話題は `check` が似た既存のタグを知らせ、毎日の見直しで人が「機能に上げる／別名にまとめる／話題のまま」を決める。別名にまとめたら、カタログの `aliases` に足す
- 英字のタグに @ を付けると、GitHub の同じ名前のユーザーに通知が飛ぶことがあるので、@ は付けない

## 5. Issue の寿命

- 立てるとき：題「機能名：何をするか」、本文に「機能：」「閉じる条件：」
- 閉じるとき：閉じる条件を満たした PR に「Closes #n」。書く前に、閉じる条件の文言のとおりに確かめるテスト（か、確かめた記録）があるかを見る。一部しか満たさないなら「関連 #n」にする（#58 から）
- やり残し：その機能の「残り」の Issue に足す（機能ごとに1つ）。分けるときは「#n の続き」
- **系譜の線になる言い方**（地図の「引き継ぎの系譜」でつながる）：Issue の題か本文に、元の Issue の番号に続けて「の続き」「の残り」「の引き継ぎ」「から分けた」「の一部」「P1」などの段（例：「#204 の続き」「#298 の残り」）。プロジェクトでは別のリポジトリも「stats2-course#577 の続き」と書ける。GitHub のサブ Issue（親子）も系譜に入る。「関連 #n」は参照で、系譜の線にはならない（#81 から。判定はコードの `HANDOFF`）
- 7日動かず、つながる機能も直近7日マージなしの開いた Issue は「古くなっている候補」になり、毎日の見直しで扱う

## 5a. 外部レビューを受けたとき

- 外部レビューを受けたら、指摘ごとの対応結果を PR の説明に記録する（直した／Issue にした／見送った と、その理由）
- 同じ目的と受け入れ条件で確認できる指摘は一つの PR にまとめる。確かめ方が違うもの（例：申告の判定と同期の正しさ）は別の PR にする
- 追加調査や判断が必要な指摘は Issue に残し、元のレビューからたどれるようにする（Issue の本文に「外部レビュー（日付）の指摘」と、対応表のある PR の番号を書く）

## 6. 決まりそのものの直し方

- 毎日の見直しで「足りなかった決まり」と守り具合を見て、決まりに足すか一回限りかを分ける
- 決まりを変えるときは、この文書・`CLAUDE.md`・`README.md` のうち、関係するものを同じ PR で直す
- 2週間使われていない画面・機能は、毎日の見直しで外す案を出す（外すかは人）
- 機能を外すときも、D1 の表とデータは残す。表を消すのは、人が個別に決めたときだけ（#33 の申告から）
- ただし、**いつでも元から作り直せる写し**（PR の説明の要る行＝digest、文書の中身の写し＝rule_texts など）は「残すデータ」に入れない。作り直しのために空にしたり消したりしてよい。そのときは PR に、何が写しで、何から作り直すかを書く（#61・#82 から）

## 6a. 画面の決まり

- **画面はどのリポジトリ（プロジェクト）の話かを持つ**。表示・保存（判断の印など）・読み込みは、同じリポジトリ（プロジェクト）を使う。切り替えの途中に届いた古い答えは捨てる。保存の宛先は、表示しているもののリポジトリにする（#76 から）
- 住所（URL）で開ける画面は、住所にもリポジトリを入れる（例：`#repo=…&lineage=411`）

## 7. ほかのリポジトリに広げる

1. まず idea-flow 自身で続ける（2週間をめど）
2. 守り具合が上がり、地図のつながりが確かになったら、weather-note-cf に広げるかを人が決める
3. 広げるときは、`CLAUDE.md` の書き方の節と Issue のひな形を、そのリポジトリへの PR で出す（出す前に相談）

## 8. 困ったとき

| こと | 見る所・すること |
| --- | --- |
| マージしたのに本番に出ていない | main のチェック「Workers Builds」。失敗なら Cloudflare のビルドの記録を人に開いてもらう。ビルド用の鍵が切れていたら（「組織を離れたユーザーのトークン」）、Worker の設定 → ビルド → API トークンを作り直して再試行（2026-11-27 に一度あった） |
| 地図に「読めませんでした」 | GitHub の鍵（`GITHUB_TOKEN`）に、そのリポジトリの Pull requests・Issues の読み取りがあるか |
| コネクタの地図が古い | `sync` で読み直す（ふだんは読むとき30分ごとに自動） |
| つながりが少ない | 書き方（PR に Issue の番号）が守られているかを守り具合で見る |
