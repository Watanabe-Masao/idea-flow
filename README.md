# idea-flow

開発の地図を見せる道具。機能ごとの作業・Issue の経過・決まりの文書を GitHub から読み、人と Claude が同じ地図を見て開発を進める。
読むだけで、リポジトリには書き込まない。決めるのは人。

- **地図**：機能の一覧（カタログ）と、マージした PR・Issue から、機能ごとの稼働・状態・Issue の経過を自動で作る
- **文書**：決まりの文書（CLAUDE.md・スキル・docs）の一覧と届き方、気になる所（重複・食い違い・古い決まり・どこからも読まれない文書）
- **コネクタ（MCP）**：Claude が同じ地図と文書を読む

> 以前あった「タスク管理（Linear・コミットの時系列）」と「範囲の木・変更リクエスト・範囲のボード・作業の記録・レントゲン・CLAUDE.md の書き出し」は外した（2026-11）。D1 の表（scopes・change_requests・rule_summaries など）は消していない。

## 地図（機能ごとの稼働と Issue）

画面の最初の「地図」。**機能の一覧（カタログ）**と、マージした PR（変えたファイル）・Issue から自動で作る。読むだけで、リポジトリには書かない。

- **カタログ**：`src/catalogs.ts`。機能ごとに、名前・入口・ファイルの正規表現・使うデータ・題の頭の言葉。いまは weather-note-cf だけ（2026-11-27 にコードを読んで作った22機能）
- **稼働**：機能ごとに、1日にマージした PR の数をマスの濃さで（3週間／2か月）。マスをなぞると、その日の PR が下に出る
- **状態**：その機能のファイルを変えた PR のマージの数そのままで言う。直近4日に3件以上マージ／直近7日にマージあり／直近7日マージなし（「止まっている」と決めつけない）
- **Issue**：本文の「機能：」の行 → カタログで人が結び付けたもの → 題の頭（「満月の物語：…」）→ 題の言葉、の順に機能へ結び付ける。つながる機能がすべて止まっていて、7日以上動いていない開いた Issue は「古くなっている候補」
- **申告**：PR の説明に「確かめた決まり」「決まりになく、自分で判断した所」「足りなかった決まり」があれば、機能の最近の作業に出す
- **どの機能にも当たらない作業**：カタログに足すかを決める材料
- **つながりの確かさ**：親子（GitHub のサブ Issue）＞ これで閉じた・番号で参照 ＞ 引き継ぎ（本文の「#299 P2」「の続き」から推定）＞ 推測（候補）。推測は「関連：なし」の PR と、Issue を立てた時刻より前のマージを除く
- **Issue を起点に（スマホ）**：クラスターで機能か話題を選び、Issue を押すと、その直下につながる PR・Issue が種類ごとに全部（根拠・GitHub へのリンクつき）。「Issue の経過で見る」で、その Issue を中心に経過へ移る
- **タグ（複数の入り口）**：本文の「タグ：コールドムーン、絵本」（3つまで）。機能の名前・別名ならその機能にも入り、それ以外は「話題」としてクラスターの入り口になる。新しい話題は自己チェックと毎日の見直しで扱う
- **クラスター**：機能ごとに、その機能の Issue（左）と、つながる PR（右）を線で結ぶ。線の種類＝つながりの種類（閉じた・番号で参照・引き継ぎ・推測・機能の割り当て）。Issue はつながる PR の高さに置く。四角を押すと、そのつながりだけを残して根拠を出す。推測は隠せる。PR は新しい24件まで
- **Issue の経過**：「Issue の経過」に切り替えると、Issue ごとに立てた日から閉じた日（開いているものは今日）までを線で、つながるマージ（PR）を点で（同じ日はまとめて件数）。開いている Issue の数の移り変わりも出す
- **つながりと根拠**：Issue を押すと、つながりを種類ごとに、根拠（どこに書いてあったか）つきで出す
  - これで閉じた（PR の closingIssuesReferences）／番号で参照（PR の題・説明、Issue の題・本文の「#番号」）
  - 引き継ぎ元・引き継ぎ先（「#299 P2」「#142 の続き」「の残り」など）。Issue どうしのつながりも出す
  - 推測（候補）：開いている Issue と同じ機能のファイルを、その Issue が開いていた間に変えた PR（ほかの Issue を番号で指す PR と、見た目・文書・テストだけの PR は除く。新しい5件まで）。確定ではない
  - Issue の本文は4,000字で切って保存するので、切る前に「#番号」とその行を取り出す
  - 「この Issue を中心に」で、その Issue と、つながる Issue だけにする
- **データの流れ**：データ（外から取る・自前で貯める）と機能のつながり。貯めているのにどの画面も使っていないデータは赤い破線
- 取り込み：2つに分ける。**最近の更新**（新しく動いた PR を、前回の最終成功時刻に届くまで。届かなければ続きの位置を保ち、次に続きから。届いたら最終成功時刻を進める。Issue もここで読み直す）と、**さかのぼり**（PR を古い順に50件ずつ、続きの位置を覚える）。画面とコネクタが重なったら、D1 のロック（2分）を取れなかった方は保存済みの地図を返す。書き込みはすべて「ロックがまだ自分のものなら」の条件つきで、遅れた古い処理は上書きできない

## スマホだけで動かす（Cloudflare の Workers Builds）

1. D1 に `idea-flow` を作る（作成済み。ID は `wrangler.jsonc` に記入済み）
2. Workers & Pages →「作成」→「リポジトリをインポート」→ このリポジトリ。デプロイコマンドは `npm run deploy`
   （表の作成〔マイグレーション〕→ デプロイの順に自動で行う）
3. Worker の「設定」→「変数とシークレット」に、シークレットとして `ADMIN_TOKEN`（画面の合言葉）・`GITHUB_TOKEN`（読むだけ）・`MCP_TOKEN`（コネクタ）を追加
4. Worker の URL を開き、合言葉を入れて「文書」から決まりの文書を取り込む（地図は開くと GitHub から読む）

`GET /api/selftest`（合言葉つき）で、bge‑m3 が動くか・次元数を確かめられる。

## 文書（決まりの見える化）

画面の「文書」。リポジトリの CLAUDE.md・AGENTS.md・ROLE.md・SKILL.md・決まりの文書（`docs/*.md` など、人が選ぶ）を**読むだけ**で取り込み、どこに効いているかと問題を表示する。GitHub には書き込まない。

- 文書ごとに「どう読まれるか」を出す：自動で読まれる（CLAUDE.md・AGENTS.md）／役割として（ROLE.md）／説明文で読まれる（スキル）／参照されたときだけ
- 見つける問題：重複・食い違いの候補・一時的な決まりの残り・読み込まれ方が重なるスキル・どこからも読まれない文書
- 機能していない・意味がなさそうな文書の候補（取り込みのたびに、リポジトリの .md を全部見る）
  - もう無いファイルを指している：文書に書かれたパスがリポジトリに無い。消したコミットも出す（同じ行に「消した」などと書いてある記録は除く）
  - 使っていない技術向けのスキル：説明文の技術（Vue・Svelte など）が package.json に無い。外から入れたスキルも対象
  - どこからも案内されていない文書：どの .md からも参照されていない（入口・フォルダの説明の README・GitHub のひな形・決まりとして選んだ文書は除く）
  - .md は GitHub の GraphQL で約40件ずつまとめて読む（GITHUB_TOKEN が要る。無いときは選んだ文書だけで調べる）
- 人が「問題ではない」にしたものは、取り込み直しても出さない
- ルールの寿命は、人が仕分けるまで「未分類」（#7 の設計の原則）
- しきい値：`rule_dup`（重複）・`rule_conflict`（食い違いの候補）・`rule_skill`（スキルの重なり）
- 取り込みは人がボタンで行う（毎朝の自動取り込みには入れない）。読むリポジトリが GITHUB_TOKEN の対象外なら、公開リポジトリだけ読める

## 書き方の決まり（地図を働かせるため）

地図のつながりは、PR と Issue の書き方で確かさが変わる。決まりは `CLAUDE.md`（Claude が毎回読む）に書き、地図に「書き方の守り具合」を出す。

- PR の題「機能名：何をしたか」／PR の説明に「Closes #n」か「関連 #n」／最後に申告の3つの見出し
- Issue の題「機能名：何をするか」／本文の最初に「機能：」「閉じる条件：」（ひな形 `.github/ISSUE_TEMPLATE/work.md`）
- やり残しは、その機能の「残り」の Issue に足す。分けるときは「#n の続き」
- 新しい機能は `src/catalogs.ts` に足す
- 守り具合：その期間の PR と立てた Issue について、それぞれの書き方を守った割合と、足りないものの一覧（地図・コネクタの map）
- まず idea-flow 自身で試す（カタログに idea-flow の8機能を入れた）。weather-note-cf に広げるかは、様子を見て決める

### Claude のコネクタ（MCP）

Claude が作業の前に、人と同じ地図を読むための入口。**読むだけ**（リポジトリにもアプリのデータにも書き込まない）。道具は `idea_flow` ひとつで、`action` と `args` を渡す。

- `rules`：書き方の決まりと、使える機能名の一覧（CLAUDE.md を読まない AI も、これで同じ決まりで作業できる）
- `check`：自己チェック。出す前は下書き（kind・title・body・files）、出したあとは PR か Issue の番号。✓／✗ と直し方を返す
- `map`：地図の全体（機能ごとの状態・開いている Issue・古くなっている候補・どの機能にも当たらない作業）。最初に読む
- `feature`（args: id か name）：機能の中身（使うデータ・最近の作業と申告・開いている Issue）
- `issue`（args: n）：Issue の周辺（つながりの種類と根拠）
- `review`：毎日の見直し（実装担当者がその日の最初の作業の前に読む）。前回からの新しいものを、自分で直すもの／人に決めてもらうもの／待っているもの に分ける。読むと見直した時刻が残る。運用は `docs/operation.md`
- `issues`（args: state）・`sync`（GitHub から読み直す。ふだんは読むときに30分ごとに自動）
- 文書：`overview`・`findings`・`read_doc`・`search`

つなぎ方
1. Cloudflare の「変数とシークレット」に `MCP_TOKEN` をシークレットで追加する（長いランダムな文字列）
2. Claude の設定のコネクタで、カスタムコネクタを追加し、URL に `https://<Worker のURL>/mcp/<MCP_TOKEN>` を入れる

> 合言葉は URL に入っているので、URL を人に見せないこと。漏れたら `MCP_TOKEN` を変えれば古い URL は使えなくなる。
